# Spec: Sync saved logs to destinations (PokeDojo first)

Status: **Approved** (2026-10-12)
Builds on: [ADR 0005](../adr/0005-uploads-deliver-saved-logs.md), follow-up #4 in the
[extraction spec](2026-10-11-capture-app-extraction.md#follow-up-specs).
Depends on: the PokeDojo receiving-side spec in `pokedojo.pro` (token page, endpoint, games
without a deck).
Vocabulary: [`GLOSSARY.md`](../../GLOSSARY.md).

## Goal

Back-to-back play with no extra steps: every saved log reaches the player's account on a
site automatically, without interrupting the game. PokeDojo is the first destination.
The capture side is generic, so other sites (TrainingCourt next) only need to accept the
same envelope and publish a destination config.

## Decisions

| # | Decision | Why |
|---|---|---|
| D1 | A site publishes a **destination config**; the player pastes it once in settings | Sites we don't know about yet can integrate without an app release. One-time setup, so paste is enough |
| D2 | Auth in v1: static bearer token, either embedded in the config or pasted by the player when the config asks for it. Tokens live in the OS keychain, never in `settings.json` | Cheapest thing a site can ship. Browser sign-in (OAuth/device flow) costs every site at least as much and adds refresh; the config is versioned so it can be added later |
| D3 | Every delivery sends one **envelope** (below). No per-site body template in v1 | One documented contract for sites. Templates (e.g. Discord) are a later, additive change |
| D4 | No parser analysis in the envelope; Rust delivers the raw log | Analysis is TS-only; delivering from Rust works with no webview. The log is the source of truth; sites parse it with the public npm parser |
| D5 | `playerName` is optional; omitted when the player hasn't set one | Like a game with no deck, the site resolves it later. Sync never waits on settings |
| D6 | A log saved from the results screen is delivered once its save can no longer be undone: after the results screen goes away (Continue, or next match). Any other save is delivered immediately | Undo never races the network; no remote-delete contract. Outside the results screen there's no Undo to wait for |
| D7 | Deleting a match locally never deletes it remotely | Keeps the site contract to one endpoint |
| D8 | Persistent delivery queue keyed by (saved log, destination), in SQLite in the app data folder. Transient failures (network, 5xx, 429) retry with backoff for ~24h, then fail. 401/403 mark the destination **needs attention** and pause its deliveries (they stay pending) until the player saves a new token. Other 4xx fail that delivery at once. Redirects aren't followed (the token stays with the configured URL), so 3xx fails too | Survives restarts and offline play; doesn't hammer a site with a bad token, and a token fix needs no per-log retries. One rejected log can't pause a destination |
| D9 | UI: per-match sync status (pending / synced / failed) on the row, with each destination's status and last error in the match detail; a badge on the capture drawer handle and the Settings tab only when a destination needs attention. No toasts during play | Failures are visible but never break flow |
| D10 | Only logs saved after a destination is connected are queued. Any match, including older ones, can be synced from its `⋯` menu: **Sync to {destination}**, one item per enabled destination (reads **Retry sync** when that delivery failed, **Retry sync to {destination}** when several are enabled). No bulk backfill in v1 | Reuses the existing row menu; the same action covers backfill and retry |
| D11 | No Test button in v1; the first delivery is the test | A bad token surfaces as "needs attention" (D8). Avoids a dry-run contract every site must honour |
| D12 | Ship PokeDojo end to end first; then document the site contract and propose TrainingCourt's side | One real consumer shapes the contract before it's generalised |

## Destination config (v1)

What a site's "Copy config" button produces. JSON, so a later deep link can carry the
same payload.

```json
{
  "ptcglTrackerDestination": 1,
  "name": "PokeDojo",
  "url": "https://pokedojo.pro/api/battle-logs",
  "auth": { "type": "bearer", "token": "pdj_…" }
}
```

- `auth.token` is optional. Without it, the config must give `auth.tokenUrl`, and the app
  asks the player to paste a token from that page.
- Method is always `POST`; body is always the envelope. Extra static `headers` (visible
  ASCII values, each name once) are allowed; `Authorization`, `Content-Type`,
  `Content-Length`, and `Host` are set by the app.
- `url` and `tokenUrl` must be `https`.
- Unknown fields are rejected so typos surface; adding a field bumps
  `ptcglTrackerDestination`.
- Import shows a confirmation (name, host) before saving. On save the token moves to the
  keychain and the rest goes to `settings.json`.
- Several destinations may be configured; each gets its own deliveries.
- A destination is identified by its `url`. Pasting a config for a URL already configured
  updates it in place: same deliveries and enabled state, new name, headers, and token (a
  new token clears needs attention). Without a token, the current one is kept.

## Envelope (schema 1)

```json
{
  "schemaVersion": 1,
  "log": "<battle log text>",
  "playerName": "<player name, omitted when unset>",
  "savedAt": "<RFC 3339>",
  "appVersion": "<semver>",
  "deck": "<optional; omitted unless this destination opts in>"
}
```

`deck` carries the match's decklist, format, player archetype, optional opponent
archetype, and optional identity metadata. Its shape and delivery rules live in the
[deck identity spec](2026-10-24-deck-identity-integration.md); a destination that does
not accept it must keep the per-destination **Send deck identity** switch off.

Sites must treat the request as idempotent: the same `log` sent twice creates one game.
Any 2xx counts as delivered.

## Capture side

- `LogSink` stays the single save entry point (ADR 0005). A successful save records a
  delivery per enabled destination: held until the results screen goes away when saved
  from it, otherwise ready at once (D6).
- Undo drops held deliveries.
- A Rust delivery worker drains the queue; HTTP from Rust, so no webview CORS question.
- If the queue database can't be opened, the app falls back to an in-memory queue and logs
  the error: saving logs never depends on sync.
- Keychain access goes behind a port (ADR 0004), so Windows can supply its own.
- Settings: Destinations section with Paste config, enable/disable, Send deck identity
  (per destination, default off), and Remove (also deletes the keychain entry). A
  destination that needs attention shows why and offers Paste token (with a link to its
  token page, when it has one) and Retry sync, which resumes it with the current token.

## PokeDojo side

Specced in `pokedojo.pro`. This spec fixes only the contract it must meet: a page that
mints a per-device, revocable, write-only token and copies a destination config; and
`POST /api/battle-logs` accepting the envelope, idempotent on the log, storing the game
without a deck for the player to assign later.
